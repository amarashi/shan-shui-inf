# Performance of the embedded painting

Generated by `pnpm perf:embed` (tools/perf-embed.js) on 2026-10-02, Chromium 151.0.7922.34, headless, on the same Windows 11 desktop machine as docs/baseline.md. The demo page mounts the coast in `static` mode (hero, height 220 to 420 px) plus a second 180 px painting.

- **ready**: navigation start to the hero painting being visible (`mount().ready`: first view and paper generated in the worker and inserted).
- **longest task**: longest main-thread task while loading. Generation runs in the worker, so this is mostly inserting markup.
- **elements**: SVG elements on screen in the hero.

Budgets (PLAN.md Phase 6, proposed against docs/baseline.md): ready within 1500 ms on the throttled phone profile (upstream: about 2,800 ms throttled for its first screen), longest main-thread task under 200 ms (upstream: 2,600 to 4,200 ms throttled), on-screen elements under 15,000 (upstream: about 41,000).

## Bundle size

`pnpm build` (Vite library mode, minified, gzip -9 measured on 3 October 2026): a page that uses `<coast-inf>` loads `element.js` (0.5 kB gzipped), the `mount` chunk (4.0 kB) and the worker (27.2 kB): about **32 kB gzipped**, against the plan's budget of about 60 kB. `coast-inf.js` (32 kB gzipped) also carries the generator for `renderToSVG()`; bundlers drop it when only `mount` is imported (`sideEffects` is set in package.json).

## Caveats

- "Longest task 0 ms" means no main-thread task reached Chromium's 50 ms long-task threshold: the worker generates, and each chunk's markup is inserted as it arrives, in small pieces.
- Chromium's CPU throttling is applied through the page's DevTools session; it is not confirmed that it slows the worker by the same factor, so the throttled "ready" times may flatter generation. On a real low-end phone, expect generation to take longer while the main thread stays free.
- The demo page is served by Vite's dev server (unbundled modules). The production build loads fewer, smaller files.
